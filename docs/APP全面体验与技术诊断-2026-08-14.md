# 颐养年 APP 全面体验与技术诊断

> 审计日期：2026-08-14
>
> 审计对象：当前 `codex/total-purchase-analytics` 分支的 Flutter APP、Supabase 数据结构与迁移脚本
>
> 已确认主要使用端为 Android 手机；任务优先级依次为：进货/出货/库存管理，新增用户/储值/消费，查看分析。

## 2026-08-15 业务确认与实施状态

- APP 永久只有一个门店，但多个账号之间不共享数据。已提供 `016_account_isolation.sql`，线上执行前必须备份并显式填写历史正式数据的账号 UUID。
- 一张进货单允许包含多个商品。已将进货编辑器改为多条明细，并对历史数组错位记录禁止保存，避免静默丢失。
- Android 首页和底部导航优先库存管理，手机库存列表改为单列卡片后进入独立详情；客户和分析依次后置。

## Executive Summary

- **当前最需要解决的不是视觉换肤，而是数据安全与一致性。** 数据库策略允许任意已登录账号读写全部业务数据，演示/正式数据仅靠客户端名称和备注规则过滤；客户与储值级联删除由客户端分步执行，失败时可能留下部分删除状态。
- **历史进货记录存在高风险编辑路径。** 数据结构允许一条进货包含多个商品，但当前编辑页只读取第一项，并在保存时写回单项数组；编辑历史多商品记录可能静默丢失其余商品。
- **登录保持与性能问题都来自启动链路。** 诊断时冷启动会主动清除 Supabase 已恢复的有效会话，导致用户每次重填账号密码；已登录启动页还把首页与完整分析预加载放在进入首页之前，分析页存在按客户、按储值逐条查询的 N+1 请求。
- **移动端界面把桌面信息密度直接压进手机宽度。** 库存和客户详情使用固定左右分栏、11–13px 字号和缩小点击区域；分析页则先展示大量筛选器，再给用户结论，均不符合店铺现场快速操作的场景。

## 结论：先止损，再提速，最后统一体验

本次共归纳 21 个需要进入整改清单的问题：P0（数据/业务安全）3 个、P1（核心任务受阻）15 个、P2（设计一致性与长期维护）3 个。建议按以下顺序推进：

1. 阻断多商品进货记录的静默覆盖，并确认未来进货单模型。
2. 确认单店共享还是多账号隔离，随后重构 RLS 与数据归属。
3. 将客户/储值级联删除迁移为数据库事务或 RPC，避免部分成功。
4. 重构启动和分析请求，先进入可操作首页，分析按需加载并批量查询。
5. 把库存、客户详情改为手机端“列表 → 详情”的单列任务流。
6. 统一只读、编辑、删除、错误、加载、空状态和设计令牌。

## 最高优先级风险

| 优先级 | 问题 | 已验证证据 | 用户影响 | 建议动作 |
|---|---|---|---|---|
| P0 | 已登录账号可读写所有数据 | `003_rls.sql` 与库存迁移均使用 `USING (true)`；演示/正式隔离发生在客户端 | 新增账号后可能跨账号看到或修改全部客户、储值、消费和库存 | 先确认账号/门店模型，再增加 `owner_id` 或 `store_id` 并收紧 RLS |
| P0 | 编辑历史多商品进货可能丢数据 | 表和模型是三个并行数组；编辑页只取 `.first`，保存时只写一个元素 | 用户只是修改金额或备注，也可能覆盖其余商品 | 确认“一单多商品”还是“一条记录一个商品”；确认前禁止编辑多商品历史记录 |
| P0 | 级联删除不是原子事务 | 客户删除逐条删消费、再删储值和客户；储值删除也是两步客户端请求 | 网络中断或权限异常会造成部分删除、数据不一致 | 改为数据库外键级联或事务型 RPC，并补恢复/审计策略 |

## 核心体验问题

### 1. 启动与登录：等待太早，错误太技术化

- 诊断时 `AuthService` 只认可本次进程内的显式登录，并在冷启动发现本地持久化会话时主动退出，直接造成用户每次打开 APP 都要重新填写邮箱密码。本轮已改为恢复有效会话，主动退出、切换账号或会话真正失效时才返回登录页。
- 已登录启动页先并行加载客户树和完整店铺分析，每项最长等待 18 秒，同时设置 12 秒兜底；之后还会检查更新。首页可操作时间被非首屏分析数据拖慢。
- 登录页另外暴露“测试连接”任务，失败文案直接出现 Supabase、SQL、项目暂停、VPN 等技术信息。普通店员无法据此处理，也容易误以为需要维护后台。
- 建议：首页只加载首屏最小数据；分析和更新检查转为后台任务。登录页自动诊断网络，用户只看到“网络不可用 / 服务暂时不可用 / 账号信息错误”，技术详情写入日志或管理员诊断页。

### 2. 客户：同一层级同时承担展开与跳转

- 客户列表一行既可点击展开储值，又通过右侧入口进入详情，用户无法预判点击同一张卡片的结果。
- 客户详情同时存在页面级编辑、字段级铅笔编辑和删除，编辑模型不一致；详情内又使用固定左右分栏展示储值和消费。
- 建议：客户卡整行统一进入详情；若需要快速展开，使用明确的“展开储值”按钮。详情默认浏览态，进入编辑态后统一保存/取消；手机端以分段卡片和二级详情替代左右分栏。

### 3. 库存：手机上强行使用主从分栏

- 500px 左右宽度下仍使用 3:5 左右分栏，小项名称、库存摘要、关联记录和五类操作被压缩在同屏。
- 列表信息使用 11px/13px 字号，多处按钮主动缩小点击区域；对高龄员工、单手操作和店铺现场快速核对都不友好。
- 同一页面同时放“补充入库、出库、重命名、删除、归类大项”等操作，缺少主次与风险分层。
- 建议：手机端改为“库存小项列表 → 小项详情”；列表只保留库存量和异常状态，详情页顶部放主操作“入库/出库”，管理类操作收进更多菜单，删除置底并二次确认。

### 4. 店铺分析：先让用户配置，再告诉用户结果

- 首屏先出现大量大项筛选标签和日期控制，经营结论、异常和行动建议被推到后面。
- 页面同时容纳周期汇总、总进货、消费结构、日历、储值排行和生日提醒，单页过长且模块目的不同。
- 总进货口径已经可下钻，但解释文本过长，关键数字、同比/环比和异常提示不足。
- 建议：第一屏只显示“本周期收入/储值/进货/消费次数”与变化、异常；筛选器收进可折叠条件区。将“经营概览、客户运营、库存经营”拆为二级页面或分析页内部标签。

### 5. 视觉与无障碍：有品牌色，但没有完整设计系统

- 主题定义了基础颜色、按钮、输入框和卡片，但 APP 固定浅色；缺少统一字号层级、间距、导航、弹窗、提示、危险动作和状态色规范。
- 多个核心页面直接写死 11–13px 字号、灰色文本和紧凑点击区域，没有看到针对系统字体放大、窄屏、键盘或屏幕阅读器的测试。
- 建议：建立最小设计令牌（8pt 间距、字号层级、圆角、阴影、语义色、最小 44/48px 点击区域），再按高频页面逐步替换，避免只做一次性“美化”。

## 技术性能与工程质量

### 请求与缓存

- 分析预加载按客户逐个计算累计储值，又按消费关联的储值 ID 逐条查询；当前代码审计检出 39 处 `getAll()` 调用和 13 处循环/链路中的 `getById` 等逐条读取迹象。
- 多数列表没有分页或服务端聚合。数据量小的演示环境看似可用，但真实数据增长后会增加网络往返、内存和渲染负担。
- 缓存存在，但失效粒度和页面加载逻辑分散在各页面；单个分析页面超过两千行，同时管理加载、筛选、缓存、下钻、日历和生日逻辑，修改风险高。
- 建议：增加批量查询与服务端聚合；对长列表分页；将分析拆为查询服务、领域计算和多个展示模块；用统一的查询状态管理处理缓存、刷新和错误。

### 数据一致性

- 进货使用三组并行数组保存大项、小项和数量，必须依赖数组长度及索引永久对齐。现有消费/库存计算只能取三者共同最短长度，异常数据会被静默忽略。
- 客户以姓名作为关联键，改名依赖特定迁移中的 `ON UPDATE CASCADE`；业务主键可变，迁移漏执行时会直接失败。
- 建议：进货改为“进货单头 + 进货明细行”；客户关联使用不可变 ID；关键写操作用事务和数据库约束保证完整性。

### 错误与可观测性

- 未识别异常会把原始错误字符串直接显示给用户；全局异常在 Release 模式仍主要 `debugPrint`，代码注释写“可上报”，但没有实际崩溃与性能监控闭环。
- 建议：统一错误码和用户文案，保留可复制的短错误编号；接入崩溃、慢请求、启动耗时和关键写失败监控，且不上传客户隐私数据。

### 自动化基线

- `flutter analyze` 当前报告 124 项问题，包含异步后继续使用 `BuildContext`、死代码、废弃 API、未使用字段等。
- 诊断开始时 17 个核心工具单测通过、唯一整应用 Widget 测试因 Auth 直接依赖全局 Supabase 而失败。本轮将 Supabase 客户端改为依赖注入后，完整测试已恢复为 18/18 通过；核心业务页面的回归覆盖仍不足。
- 测试目录只有 5 个测试文件，核心客户、储值、消费、库存、分析与导航流程没有端到端覆盖。
- 建议：继续为 P0 数据写入、浏览/编辑态、返回上下文、统计口径和窄屏布局增加回归测试。

## 目标产品结构建议

### 一级导航

1. **工作台**：今日待办、近期生日、快捷新增消费/储值、异常提醒。
2. **客户**：客户列表、搜索、客户详情、储值与消费历史。
3. **库存**：库存状态、入库/出库、盘点与进货历史。
4. **分析**：经营概览、客户运营、库存经营；默认先结论后筛选。

设置继续作为头像/更多入口，不占用与高频业务同等的一级导航位置。该调整取决于真实主用户与每日工作流，需确认后实施。

## 分阶段整改计划

### 阶段 0：立即止损

- 检测历史多商品进货记录，浏览态提示并禁用高风险编辑，直到业务模型确认。
- 为所有删除/覆盖类操作补充明确对象、影响范围和二次确认。
- 恢复 Supabase 有效登录会话，取消冷启动时的主动退出。
- 修复 Widget 测试基础设施，建立可重复回归基线。

### 阶段 1：性能与数据安全

- 首页最小化加载；分析与更新后台化。
- 批量替换分析 N+1 请求，增加服务端聚合与分页。
- 按确认后的账号模型新增数据归属字段与 RLS；写迁移、回滚和数据校验脚本。
- 将级联删除与关键写操作迁到数据库事务。

### 阶段 2：核心任务流重构

- 库存和客户详情改为移动端单列导航。
- 统一浏览态/编辑态/保存/取消/离开保护。
- 分析首页改为“结论 → 异常 → 行动 → 筛选/明细”。

### 阶段 3：设计系统与持续质量

- 建立设计令牌和共用组件，系统修复字号、间距、点击区域、状态和错误反馈。
- 增加窄屏、系统字体放大、弱网、离线和大数据量测试。
- 建立启动耗时、页面加载、写失败、崩溃率等体验指标。

## 仍需要确认后再改的问题

1. **历史数据归属**：执行账号隔离迁移前，需要管理员确认历史正式数据所属账号的 `auth.users.id`；代码不会根据邮箱或数据内容自动猜测。
2. **进货明细长期存储模型**：当前在保持兼容的前提下继续使用三个并行数组。若未来需要单商品单价、批次、供应商或部分退货，再确认是否迁移为“进货单头 + 明细表”。

账号模型、一单多商品和一级导航已按确认结论实施；上述两项仍需在触及线上数据或扩展字段前确认。
